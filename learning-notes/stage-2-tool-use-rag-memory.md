### Task 1：检索增强生成（RAG）

完成时间：2026-07-18

代码：`stage-2/rag.py`

核心概念：

RAG（Retrieval-Augmented Generation）解决的核心问题：模型的参数记忆是静态的、有限的，不包含你的私有数据，也可能过时或产生幻觉。RAG 的思路是——回答问题前，先从外部知识库里检索相关内容，再把检索到的内容作为上下文喂给模型，让模型基于真实材料回答，而不是凭参数记忆瞎编。

一个最小 RAG pipeline 分四步：

```text
文档 -> chunk（切块） -> embed（向量化） -> retrieve（检索） -> answer with citations（带引用回答）
```

1. **Chunk（切块）**：把长文档切成较小的片段。整篇文档做一个向量会把不同主题的内容混在一起，语义太模糊，检索精度差；模型的上下文窗口也有限。常见做法是按固定 token/字符数切块，块之间留 overlap，避免关键信息正好被切断在边界上。chunk 太小丢上下文，太大降低检索精度、浪费上下文窗口。
2. **Embed（向量化）**：用 embedding 模型把每个 chunk 转成向量，语义相近的文本距离更近——这和关键词搜索（如 BM25，只匹配字面词）的本质区别。查询也要用同一个 embedding 模型转成向量才能比较。
3. **Retrieve（检索）**：拿查询向量和所有 chunk 向量算相似度（常用 cosine similarity），取 top-k。实际系统常用 hybrid search（向量+关键词）融合排序，因为纯向量检索有时会漏掉需要精确匹配的专有名词、代码符号、编号。
4. **Answer with citations（带引用回答）**：把检索到的 chunk 作为上下文塞进 prompt，要求模型标注每个结论的来源。让答案可验证、降低编造空间；检索不到相关内容时应让模型说"没有找到相关信息"而不是硬编。

检查题修正：

1. 检索到不相关 chunk 的原因不止 chunk 太大/top-k 设置，还包括 query 表述模糊、embedding 模型对领域词汇语义捕捉不好、ANN 近似检索的召回误差、文档本身噪声。缓解手段除了调 chunk 大小和设阈值，还应有 hybrid search 和 reranker 二次排序。
2. chunk 太大的"超出上下文窗口"其实是两层限制：embedding 模型自身的输入 token 上限（chunk 被截断丢内容）和最终喂给 LLM 的上下文窗口（多个大 chunk 拼起来超限）。chunk 太小除了丢上下文，还有语义碎片化、chunk 数量暴增带来的存储/检索开销、overlap 占比过高造成冗余等后果。
3. 理解偏差：用户认为"引用了不存在的编号"是检索阶段漏检专有名词导致的，实际上这是两个不同的故障点。"要求引用来源"本身不会自动降低幻觉——模型仍可能编一个看似合理的编号；真正起作用的是系统侧的**程序化校验**（检查模型给出的引用 id 是否真的在检索结果集合里）。"引用编号不存在"说明的是生成阶段约束缺失 + 缺少后处理校验，跟检索漏检无关。
4. 正确：检索不到相关内容应设相似度阈值短路，返回"没有找到相关信息"，不编造。

实践产出：`stage-2/rag.py` 包含 `chunk_text`（带 overlap）、`embed`（词频向量代替真实 embedding）、`cosine_similarity`、`retrieve`（top-k + 相似度阈值过滤）、`mock_llm_answer`（带引用编号回答 + 无匹配时明确说未找到）、`validate_citations`（校验回答里的引用 id 是否都在检索结果集合里，对应检查题 3 的修正理解）。

验证：`python3 stage-2/rag.py` —— 场景 1（"RAG 的核心步骤是什么？"）命中 doc2 相关 chunk 并带引用编号；场景 2（"今天天气怎么样？"）相似度全部低于阈值，返回"没有找到相关信息"，未编造内容。

### Task 2：把搜索、数据库、文件、浏览器、代码执行接成工具

完成时间：2026-07-18

代码：`stage-2/tools_safety.py`

核心概念：

Stage 1 已经讲过"工具"的通用结构：函数 + schema（给模型读的描述）+ 注册表（名字到函数的映射）。Task 2 要讲的是——不同类型的真实世界工具，风险和设计约束差别很大，不能用同一套心态对待所有工具。

按风险和副作用，可以把常见工具分成几类：

1. **搜索（Search）**：外部网络调用，只读、无副作用，但延迟不可控需要超时；返回结果可能很大，需要截断或摘要；结果可能为空或不相关，工具要能表达"没搜到"。
2. **数据库（Database）**：一旦允许模型拼 SQL 或有写权限，风险陡增。必须用参数化查询（parameterized query）防 SQL injection，不能字符串拼接；权限最小化（只读账号、限定表/列）；返回结果限行数/大小。
3. **文件（File）**：模型给的路径必须做路径规范化 + 白名单目录校验，防**路径穿越（path traversal）**；读/写要分开设计成不同工具，写文件破坏性远高于读文件，需要更严格的路径限制。
4. **浏览器（Browser）**：本质是访问任意 URL 并执行 JS 渲染，风险比搜索更高——需防**SSRF（服务端请求伪造）**，对目标 URL 做协议/host 过滤（禁内网 IP、`file://`）；返回的渲染整页内容体量更大，需要截断/提取正文；有状态（cookie/session）要注意状态污染。
5. **代码执行（Code Execution）**：风险最高，因为模型输出直接变成可执行代码。必须**沙箱化**（独立容器/进程、限制 CPU/内存/执行时间、禁网络、禁访问宿主机文件系统/凭据）；不能用 `eval`/`exec` 直接在主进程跑；输出也要限大小。

跨工具共同原则：最小权限原则；输入校验在执行前做（不能假设模型不会生成恶意输入）；输出大小要有上限；超时是必需品；读操作和写/执行操作的风险不对等，写/执行类工具需要更严格的校验和权限。

检查题修正：

1. 完整——覆盖参数化查询、权限最小化、结果限制、执行前校验、超时，和核心概念完全对齐。
2. 完整——覆盖沙箱、资源限制、网络/文件系统隔离、避免 eval/exec、最小权限、校验、输出限制、超时，没有遗漏。
3. 方向对但少两点：(a) 超长内容不只是内容质量问题，也是成本/延迟问题——每个浪费的 token 都要花钱、拖慢响应；(b) 智能摘要之前通常先做一层便宜的兜底：HTML 正文提取（去掉导航栏/广告/脚本）+ 硬性长度上限截断，摘要是更贵的第二层。
4. 核心不对称关系（写比读更具破坏性、更难逆转）和配置加载优先级的例子都对，是很好的工程直觉。但需要澄清："文件内容不会损害"这句话容易被误读为"读取风险不大"——一个没做路径校验的读取工具本身就是严重漏洞（任意文件泄露：`/etc/passwd`、SSH 私钥、`.env`、云凭据）。读/写的不对称性是"影响范围和可逆性"的不对称，不是"读取本身安全"。

实践产出：`stage-2/tools_safety.py` 包含 `safe_db_query`（参数化查询防注入）、`run_code_sandboxed`（子进程 + CPU 资源限制 + 超时，避免 eval/exec 直接跑在主进程）、`truncate_content`（超长内容硬性截断）、`resolve_safe_path`/`read_file_safe`/`write_file_safe`（路径规范化 + 白名单校验防路径穿越）。

验证：`python3 stage-2/tools_safety.py` —— 把 `"1; DROP TABLE users; --"` 作为参数值传入查询，被当作字面字符串处理、未被当成 SQL 执行；`run_code_sandboxed` 对正常代码返回结果，对死循环代码超时后终止；`resolve_safe_path` 对 `../../etc/passwd` 拒绝，对合法子路径放行。

调试笔记：最初同时用 `RLIMIT_CPU` 和 `RLIMIT_AS`（内存上限）限制子进程，但本机沙箱化环境拒绝降低 `RLIMIT_AS`（"current limit exceeds maximum limit"）。改为只保留 `RLIMIT_CPU`，真正的兜底防护是 `subprocess.run(..., timeout=...)`——即使不设内存上限，失控代码也会在超时后被强制终止。这也印证了核心概念里的一点：**超时是必需品**，不能只依赖资源限制这一层。

### Task 3：短期上下文 vs 会话记忆 vs 长期记忆

完成时间：2026-07-18

代码：`stage-2/memory.py`

核心概念：

Stage 1 的 agent loop 里，每次调用模型都要传一个 `messages` 列表——模型没有记忆，它看到的就是这次调用里显式传进去的内容。Task 3 要区分三种"记忆"，它们的生命周期、存储位置和检索方式都不一样。

### 1. 短期上下文（short-term context）

一次模型调用（或一次 agent loop）里实际传给模型的 `messages` 列表本身。生命周期只有这一次调用/这一次 loop，loop 结束后如果不持久化就没了。它受**上下文窗口**硬性限制——不是"想传多少传多少"，而是有 token 上限，超了要么报错要么被截断。

### 2. 会话记忆（session memory）

跨越一次对话里的多轮交互，但通常局限在"这一个会话"内——会话结束（用户关闭窗口、session 过期）后，如果没有额外持久化，这段记忆也会丢失。实践上，会话记忆不是简单地"把所有历史消息原封不动一直往后堆"：

- 对话轮数一多，历史消息本身就会撑爆上下文窗口——这是会话记忆和短期上下文最直接的冲突点。
- 常见处理方式：滑动窗口（只保留最近 N 轮）、摘要压缩（把老消息压缩成一段摘要再保留）、或者两者结合（近期消息保留原文，早期消息摘要化）。

### 3. 长期记忆（long-term memory）

**跨会话**持久化的信息，存在数据库、文件或向量库里，独立于任何一次具体的对话/请求存在，除非被显式删除，否则会一直保留。和短期上下文最大的机制差异：

- 短期上下文是"直接塞进去"，不需要检索——反正就那么多，全部可见。
- 长期记忆通常**不能**直接全塞进 prompt（信息量太大，且大部分和当前问题无关），而要用类似 RAG 的方式——把当前任务/问题作为 query，检索出相关的长期记忆片段，再放进当前这次调用的上下文里。可以理解成：长期记忆是"关于用户/关于过往交互"的知识库，检索机制和 Task 1 的 RAG 是同一套逻辑。

一个具体例子就是这个 Claude Code 会话本身的记忆系统：memory 文件按 user/feedback/project/reference 分类存成独立文件，有一个索引文件汇总指向它们，新会话开始时不会把所有历史全读一遍，而是按需索引、按相关性拉取——这就是长期记忆检索模式的真实实现。

### 三者的关系

```text
短期上下文（这一次调用能看到的）
  ⊂ 会话记忆（这一次对话积累的，可能被摘要/裁剪后才进入短期上下文）
  ⊂ 长期记忆（跨会话持久化的，按需检索后才进入短期上下文）
```

三层都会遇到"信息太多装不下"的问题，只是解决方式不同：短期上下文靠硬截断/窗口限制暴露问题，会话记忆靠摘要/滑动窗口缓解，长期记忆靠检索只取相关片段。

检查题修正：

1. 完整且结构清晰（定义、来源、生命周期都覆盖）。补充两点：(a) 这也是成本/延迟问题，每多一个 token 都要花钱、拖慢响应；(b) 有个专门的现象叫"lost in the middle"——即使内容技术上塞得进窗口，模型对开头/结尾的注意力也好于中间，硬塞 50 轮不只是浪费 token，还会实际拉低答案质量。
2. 完整，持久化 + 检索两个机制差异都点到了，和核心概念完全对齐。
3. 方向对但有个概念需要澄清："会不会变"不等于"该不该存"。用户的工作、当前项目这类信息会变但仍然值得记住——真正的判断标准是 (a) 未来会话里还用得上吗、(b) 如果它会变，有没有更新/失效机制去处理（这正是第 4 题解决的问题）。"稳定性"影响的是"这条记忆需要多少维护"，不是"值不值得存"。另外还应该补一类"不适合"：纯任务本地的临时状态（这次对话进行中的细节）——不涉及隐私也不算易变，只是超出这次任务就没有复用价值。
4. 完整且成熟：分级/变更标识/二次验证、TTL 过期、变更时同步更新的 hook 机制，三层机制组合已经覆盖了"过时"和"冲突"两类问题。这套设计和这次会话本身的记忆系统的实际做法一致——同 key 覆盖更新而不是无限追加重复记录，正是这个系统的规则原文。

实践产出：`stage-2/memory.py` 包含 `SessionMemory`（滑动窗口 + 摘要压缩，超出 window_size 的老消息压缩成摘要而不是无限累积）、`LongTermMemory`（`write` 同 key 覆盖更新避免重复/矛盾记录、`retrieve` 复用字符 bigram embedding + cosine similarity、TTL 过期自动过滤陈旧记忆）。

验证：`python3 stage-2/memory.py` —— `SessionMemory` 对 5 轮（10 条消息）、window_size=2 时正确把前 8 条压缩成摘要，只保留最近 2 条原文；`LongTermMemory` 检索命中写入的 `user_job` 记录，同 key 覆盖写入后 store 仍只有 1 条记录（内容已更新为新公司），TTL 过期后（step=8，ttl_steps=5，写入于 step=2）检索结果为空。

调试笔记：最初沿用 Task 1 的按词（`\w+`）切分做 embedding，中文查询和中文内容因为没有空格分词，整句被当成一个"词"，导致查询和存储内容之间零重叠、检索不到任何结果。改为按字符 bigram 滑窗切分，查询和内容只要有局部重叠的字符对就能算出非零相似度，检索恢复正常。

## 核心概念（Task 4：处理工具失败、空结果、重复调用、幻觉引用）

Stage 1 已经建立了一个基础原则：工具错误是**观察结果**，不是终止信号——loop 不应该因为一次工具失败就崩溃，而是把错误信息喂回模型，让模型决定怎么办。Task 4 要把这个原则细化到四类具体的"不完美情况"。

### 1. 工具失败（Tool failure）

不是所有失败都该无脑重试：

- **区分可重试 vs 不可重试**：网络超时、限流（429）这类瞬时错误值得重试；参数不合法（400）、权限拒绝（403）这类错误重试了也是同样的结果，属于该立刻放弃或换一种方式，而不是重试。
- **重试要有边界**：最大重试次数 + 指数退避（exponential backoff，每次重试间隔翻倍），防止无限重试卡死 loop，也避免对下游服务造成压力。这和 Stage 1 的"最大步数"是同一类保险。
- **错误信息要对模型可读、且脱敏**：不能把内部堆栈跟踪、密钥、内部路径原样喂给模型——模型有可能在后续回答里把这些内容复述给最终用户，等于泄露。

### 2. 空结果（Empty results）

空结果是一种**合法的、明确的返回状态**，不是异常。工具要显式返回"没有查到/没有搜到"，而不是返回空字符串/空列表让模型自己瞎猜。Task 1 的 RAG 检索阈值过滤 + "没有找到相关信息"就是这个原则在 RAG 场景下的具体实现——这里要把它泛化到所有工具（数据库查询无结果、文件不存在、搜索无匹配都是同一类情况）。

### 3. 重复调用（Duplicate calls）

模型可能因为没看清之前的结果、或者陷入循环，反复用同样的参数调用同一个工具：

- 对只读工具，主要代价是浪费 token/时间/费用。
- 对**有副作用**的工具（发邮件、下单扣款、写数据库），重复调用可能造成重复的真实后果——这时候需要工具本身具备**幂等性（idempotency）**：用幂等 key/去重 token 让"重复调用"和"调用一次"产生同样的效果，而不是指望模型永远不出错。
- 系统层面的兜底：在 loop 内对相同 `(tool_name, args)` 做缓存/去重，直接复用上一次结果而不重新执行；检测"连续多次调用没有推进任务"，触发提示或提前终止（呼应下面第 4 点）。

### 4. 幻觉引用（Hallucinated references）

Task 1 讲过的"引用了不存在的编号"只是幻觉的一种具体形式。更广义地看，agent 可能在很多地方"编造"而不是基于真实执行结果：

- 编造一个工具从未返回过的内容，直接当成事实写进最终回答。
- 跳过真正的工具调用，"假装"调用过了，直接编一个观察结果继续推理。
- 编造参数值或工具名（比如引用一个不存在的文件路径、一个没被注册过的工具）。

通用防线是**不信任模型自称的"事实"**：一切结论都要能追溯到真实的工具执行记录；解析模型输出时要严格区分"这是真正的 tool_use 调用"还是"这是模型自己编的文本"，不能让编造的内容绕过执行环节直接进入回答。

### 共同原则

- 失败、空结果都是观察，交给模型处理，而不是让 loop 崩溃或者让模型胡编。
- 有副作用的操作，光靠"提示模型不要重复调用"不够，需要系统侧的幂等设计和去重兜底。
- 对模型输出（引用、结论、工具调用本身）默认不信任，需要程序化校验。
